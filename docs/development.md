## Окружение и зависимости

Единственный файл настроек пакета — [pyproject.toml](../pyproject.toml):

| Компонент | Текущее требование | Назначение |
| --- | --- | --- |
| Python | `>=3.12` | В том числе синтаксис `type` для псевдонимов типов. |
| `pdfplumber` | `>=0.11.9,<0.12` | Извлечение PDF, геометрия и таблицы. |
| `reportlab` | `>=4,<5`, extra `dev` | Генерация синтетических PDF в тестах. |
| `google-genai` | `>=2.31,<3`, extra `translation` / `dev` | Официальный SDK необязательного сетевого этапа. |
| `markdown-it-py` | `>=3,<5`, extra `translation` / `dev` | Разбор MD перед переводом. |
| `tzdata` | `>=2025.2`, extra `translation` / `dev` | Pacific timezone и DST для срока сброса суточных квот. |
| `sqlite3`, `zoneinfo` | Стандартная библиотека | Отрицательный кэш доступности и вычисление срока повторов. |
| `setuptools` | `>=68`, backend `setuptools.build_meta` | Сборка и установка пакета. |
| `unittest` | Стандартная библиотека | Исполнение тестов. |

Транзитивные зависимости устанавливаются менеджером пакетов. Lock-файла нет:
два окружения могут получить разные допустимые версии. При воспроизведении
проблемы сохраняйте фактические версии. Отдельных обязательных зависимостей
`pytest`, сервера, OCR или средств рендеринга в пакете нет.

В PowerShell из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev]'
.\.venv\Scripts\python.exe -m unittest discover -v
```

Linux/macOS:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
.venv/bin/python -m unittest discover -v
```

Активация окружения необязательна, если указан путь к его Python. Далее `python`
означает именно этот интерпретатор. Для записи состава окружения без установки:

```sh
python --version
python -m pip show pdfplumber reportlab
python -m pip freeze
```

## Запуск тестов

```sh
python -m unittest discover -v
python -m unittest discover -q
python -m unittest tests.test_headings tests.test_heading_structure -v
python -m unittest tests.test_asides -v
python -m unittest tests.test_aside_order -v
python -m unittest tests.test_frame_boundaries -v
python -m unittest tests.test_caption_continuations -v
python -m unittest tests.test_caption_narratives -v
python -m unittest tests.test_special_text_recovery -v
python -m unittest tests.test_attached_notes tests.test_rotated_content -v
python -m unittest tests.test_card_rule_fields tests.test_diagrams -v
python -m unittest tests.test_false_paragraph_boundaries -v
python -m unittest tests.test_form_inserts -v
python -m unittest tests.test_converter.CliTests -v
python -m unittest tests.test_converter.ReferencePdfTests -v
python -m unittest tests.test_translation tests.test_translation_ports tests.test_gemini tests.test_routing -v
python -m unittest tests.test_chunking -v
python -m unittest tests.test_logging -v
python -m unittest tests.test_solid_contracts -v
python -m unittest tests.test_async_translation tests.test_async_gemini -v
python -m unittest tests.test_response_recovery -v
python -m unittest tests.test_layout_recovery -v
python -m unittest tests.test_book_recovery tests.test_diagrams tests.test_table_recovery -v
python -m unittest tests.test_symbols -v
python -m unittest tests.test_table_structure tests.test_table_recovery -v
```

Команды выполняются из корня репозитория. Полный набор запускается стандартным
`unittest`, без специального test runner и без конфигурации pytest. Синтетические
PDF создаются через ReportLab в `TemporaryDirectory`; растровые изображения для
проверок подписей создаются тестовыми средствами. Постоянные результаты в
`output/` не являются входом этих тестов и не должны обновляться тестовым запуском.

### Необязательные проверки и пределы доказательства

`ReferencePdfTests` ищет `example/10. Chapter 8 Goals and Rewards.pdf`, затем
старый `example.pdf`; без обоих пропускается. `IntroductionRegressionTests`
использует `example/2. Introduction.pdf` и также пропускается без локального файла.
Общие `RecoveryRulesTests` работают без книги: графические псевдозаголовки,
сохранение настоящих буквенных/числовых заголовков, малые буллиты, висячие пункты,
жирные продолжения и границы курсивных пояснений, с отрицательными примерами.
Книжные классы в `test_book_recovery`, `test_diagrams` и `test_table_recovery`
используют соответствующие файлы `example/` и также пропускаются без них.
Генерические модельные/синтетические проверки этих модулей не требуют книги.
`OptionalLocalStructureTests` в `test_table_structure` охватывает Character Creation
11, Character Statistics 21, Gamemastering 7/21/23 и все семь сеток Animal Companions
1/2/3/6. Отсутствующий PDF пропускает соответствующий случай; синтетические span
и отрицательные проверки выполняются без частных входов.
`OptionalLocalSymbolTests` читает Introduction, Radiant Paths, Items и Combat
из `example/`; отсутствующий вход пропускает соответствующий локальный случай.
Остальные проверки `test_symbols` не требуют пользовательских PDF, включая
защиту от фильтра подписей и неизвестные знаки. Сверки карточек исключают из
обычного исходного текста только подтверждённые символы по данным каждого глифа;
целое смешанное слово, произвольные буквы, пунктуация и числа не игнорируются.
Пользовательская книга не поставляется с исходниками или пакетом. Тест чтения одиночной клавиши
Windows пропускается на других ОС; это надо учитывать при заявлении о покрытии.
Число выполненных тестов смотрите в фактическом результате запуска, а не в старом
отчёте. Пропуск не равен успешно проверенному случаю.

### Проверка постановки PDF-08

[tests/test_rotated_content.py](../tests/test_rotated_content.py) содержит девять
общих проверок и одну локальную регрессию
Adventuring. Синтетические PDF проходят реальные матрицы текста, извлечение,
фильтры, layout и оба экспорта; нейтральный случай отдельно сохраняет provenance
положительного и неизвестного знака. Локальная проверка пропускается только при
отсутствии `example/11. Chapter 9 Adventuring.pdf`. После PDF-20 она требует
три Opportunity внутри своей карточки и во всей главе, и при выборе только
физической страницы 4. Сверяются исходные глифы и координаты.

Исходная гипотеза о ненужном rotated-тексте не подтвердилась. Новых положительных
случаев удаления нет; старые проверки artist credits, обычных/фоновых подписей,
форм, таблиц и схем не ослаблялись. Это регрессии сохранения и проверка постановки,
а не приёмка нового фильтра. [Диагноз и границы](quality.md#pdf-08-проверка-постановки).

### Приёмка PDF-07

`test_paragraph_conventions` сочетает нейтральные модели с синтетическими PDF,
проходящими извлечение, определение колонок, абзацев и окончательную склейку.
Прежние отрицательные проверки `test_continuations` не ослаблены. Локальная
`OptionalEndeavorsTests` использует физические 4→5 из `example/14. Chapter 12 Endeavors.pdf`;
отсутствие частного PDF разрешает пропуск только этой проверки.

До изменения правила осмотрите полные исходные страницы и установите авторские
признаки абзаца внутри документа. Точка и одинаковый шрифт недостаточны.
Проверяйте отсутствие новых отступов, полную предыдущую строку, документные

неизменённые таблицы, игровые знаки, заголовки, схемы и отдельные блоки должны
оставаться точными. После правки кода пересоздайте затронутые ранние снимки.
Тесты и эта собственная проверка исполнителя не являются независимым аудитом.

Старые утверждения «четыре размера дают четыре глубины» и «семь размеров доказывают
переполнение» заменены отрицательной проверкой и положительными случаями с
нумерацией. Проверка допуска близких размеров дополнена возвращающимся родителем
и двумя детьми, а не ослаблена до совпадения любых результатов.

После целевого и полного офлайн-наборов корпус 02–17 проверяется строго по главе:
конвертация, полное сравнение, визуальная сверка всех изменённых контекстов,

баннерных названий допускается только с исходной областью и визуальным подтверждением.

одним завершённым прогоном. Проверка исполнителя не называется независимым аудитом.

Локальная регрессия `test_form_inserts` использует

Допустимые отличия: контейнер формы, восстановленные поля, доказанная склейка и
механическое изменение H-номеров после исключения стилей формы. Для чарника
нужен перечень полей по исходнику, включая раньше удаляемые слова и подпись.
Отдельно проверьте выбор `5`, `4-5`, `5-6`, `4,6`, несколько вставок и пропуск
внутри их цепочки. Результаты и пропуски записывайте в [отчёт качества](quality.md).
До фактического подтверждения всей матрицы PDF-03 не считается закрытой;
прохождение тестов само по себе не закрывает PDF-04…PDF-08.
Физический symlink-тест логов пропускается, если ОС/песочница не даёт права на
создание ссылки; остальные проверки логирования от этих прав не зависят.

Новые тесты не используют реальный API-ключ и запрещают живую сеть. При отсутствии
extra пропускаются проверки Markdown/SDK; для полного набора устанавливайте `dev`.
Имитация хорошего ответа доказывает работу программы, не качество русского перевода.
Живой тест с книгой выполняется только после прямого разрешения пользователя;
флаг `--send` не добавляется автоматически во время разработки. Инструкции и
полный перечень ограничений — в [разделе перевода](translation.md).

При ограничениях песочницы на системный TEMP тесты можно запускать с отдельным
существующим временным каталогом внутри `tmp/` проекта, задав `tempfile.tempdir`
перед `unittest.main`. Это настройка тестового запуска, не изменение программы.
CLI-тесты направляют технические логи во временные каталоги; библиотечные тесты
используют sink в памяти либо файлы своего TemporaryDirectory. Продакшен-логи
не читаются/очищаются тестами. Живая сеть не нужна для проверки SDK usage/таймингов.
Боевой `model-availability.sqlite3` тесты не открывают. Схема БД имеет версию 1,
журнал переводов — версию 3, контракт планирования — версию 3. Политика фрагментации
и границы пакетов включены в fingerprint; контракт 2 не возобновляется даже с прежним
ручным капом. Несовместимые старые журналы автоматически не мигрируют и не удаляются.

Async-тесты используют `IsolatedAsyncioTestCase`. На Windows event loop создаёт
служебную loopback-пару сокетов. `tests.support.allow_asyncio_self_pipe` разрешает
только создание этой пары внутри stdlib, не отключая запрет внешней сети для
провайдера. Песочница ОС может блокировать даже эту пару: тогда офлайн-набор
выполняется с разрешёнными локальными сокетами, по-прежнему с mock HTTP и запретом
реальных соединений в тестах. Это не причина добавлять `--send` или живые пробы.

Регрессия сравнения количества букв/цифр помогает найти потери и дублирование,
но сама по себе не доказывает порядок чтения, пунктуацию или абзацы. Проверки
таблиц и конкретных переходов дополняют её. Универсальной оценки точности,
процента code coverage и настроенного нагрузочного стенда сейчас нет.

## Как добавлять исправление

1. Уточнить симптом и разрешённый объём работы. По [AGENTS.md](../AGENTS.md)
   вопрос о возможности — не команда на изменение; диагностика, аудит, исправление,
   коммит и push имеют разные границы разрешения.
2. Найти дефект на соответствующем уровне конвейера: исходные слова, фильтр,
   порядок/тип блока, склейка или экспорт. Использовать `sources`, `lines` и
   физические номера страниц. Не маскировать раннюю потерю текста поздним рендерингом.
3. Добавить минимальный синтетический PDF или модельный тест с дефектом и
   соседними отрицательными случаями. Для удаления подписи обязательно проверить,
   что похожие полезные заголовок, абзац, таблица и вставка сохраняются.
4. Исправлять общие признаки, не строки/имена/фиксированные размеры одной книги.
5. Запустить целевой набор, затем полный. Проверить оба формата, геометрию,
   предупреждения и отсутствие повторных callback-вызовов для одного случая.
6. Обновить документацию контракта и карту файлов. Зафиксировать выполненные
   проверки и пропуски. Не выдавать тесты за независимый аудит результата.

Канонические `output/example.*` не обновляются как побочный эффект изменения
кода. Для сравнения создавайте отдельный результат только в разрешённом объёме
задачи и явно отмечайте, какая версия проверена. Независимого аудитора запускают
только по отдельной прямой команде; инструкция лежит в `docs/agents/`.

## Проверка и сборка пакета

Модульный и установленный запуск используют одну `cli.main`:

```sh
python -m pdf_translator --help
python -m pdf_translator --version
pdf-translator --help
```

Последняя команда требует, чтобы каталог скриптов окружения был в PATH; альтернатива
в PowerShell — `.\.venv\Scripts\pdf-translator.exe --help`.

При необходимости сборки wheel:

```sh
python -m pip wheel --no-deps --wheel-dir dist .
```

Команда создаёт сборочные артефакты; build isolation может потребовать загрузить
setuptools. Пакеты выбираются правилом `pdf_translator*`; тесты и пользовательский
PDF не являются Python-пакетами дистрибутива. Публикация на PyPI не настроена.
Версия сейчас задана в метаданных проекта и строке `--version` в `cli.py`: при
релизном изменении надо проверить оба места.

## Сопровождение документации

При закрытии задач повторных аудитов PDF-09…PDF-28 проверяйте каждое
подтверждённое вхождение из TODO, включая отрицательные контрпримеры. Координатор
отдельно запускает полный офлайн-набор и последовательный прогон частей 02–17.
Сравнение с предыдущим принятым снимком должно сохранять ячейки, значки, формы,
предупреждения и прежние контрольные сценарии; каждое изменение текста или
структуры требует объяснения и сверки соответствующего места с PDF. Ранее уже
просмотренный неизменный PDF можно использовать как источник для проверки
нового экспорта. Такой контроль изменений не следует называть новым полным
постраничным аудитом, если заново просмотрены только затронутые страницы.
Публичные тесты используют синтетические примеры; частные книги и отчёты
остаются в игнорируемых каталогах.

Схема технических событий имеет отдельную версию 1. Новые события/поля и изменения
уровней, приватности, политики файлов или CLI отражайте в [логировании](logging.md).
Не добавляйте сырые исключения/progress labels и не подключайте root/httpx/Google
handlers вместо безопасных событий. Логирование не должно менять результат,
fingerprint или число повторных API-попыток из-за собственного сбоя.

Источники документации — обычные UTF-8 Markdown-файлы. Изменение документации не
требует установки Sphinx/MkDocs. CI, автоматическая проверка ссылок, форматтер и
линтер в репозитории сейчас не настроены.

Перед каждым разрешённым пользователем коммитом нужно оценить влияние изменения
на весь комплект документации. Если изменение существенно для понимания, запуска,
разработки или проверки проекта, обновляются все затронутые разделы, а не только
README. Это касается поведения, CLI/API, моделей, алгоритмов, структуры файлов,
зависимостей, предупреждений, ограничений, тестов, рабочих процессов и инструкций.
Мелкая внутренняя правка может не требовать изменения текста, но проверка
актуальности всё равно обязательна; несвязанные разделы переписывать не нужно.

При изменении проекта проверьте:

- Новый/переименованный файл добавлен в [карту](architecture.md); ссылки относительны
  документу и ведут на существующие файлы.
- Новые параметры согласованы с `--help` и [руководством](usage.md).
- Публичные имена, поля, роли и callback согласованы с [API](api.md).
- Новое предупреждение описано в [диагностике](troubleshooting.md).
- Новая эвристика и её ограничения описаны в [алгоритме](processing.md).
- Новая проверка отражена в матрице тестов; новый раздел доступен из [оглавления](README.md).
- Планы, неизвестные настройки запуска и старые отчёты не представлены как
  реализованные возможности или подтверждение свежего результата.

### HTML-версия для телефона

Офлайн-документация находится в `output/documentation.html`: один файл с оглавлением,
внутренними ссылками, адаптивными таблицами и приложенными исходниками. Markdown
остаётся источником текста; HTML не редактируется вручную. После изменения
документации или приложенных исходных файлов HTML необходимо пересобрать, чтобы
перед коммитом он соответствовал текущему состоянию проекта.

В текущем локальном окружении используются вспомогательные скрипты:

```sh
node tmp/docs-html/build.mjs
node tmp/docs-html/check.mjs
```

Сборщик использует доступную локальную библиотеку `marked`, проверка — Playwright
и локальный браузер. Это вспомогательное окружение подготовки документа, не новые
зависимости конвертера. Скрипты в `tmp/` не отслеживаются Git и могут отсутствовать
в другой копии проекта; пути к библиотекам и браузеру привязаны к текущему окружению.
Если скриптов или инструментов нет, нужно восстановить сборку/проверку либо явно
сообщить о препятствии, а не считать старый HTML актуальным.

Проверка должна подтвердить, что все разделы включены, внутренние ссылки работают,
на узком экране нет горизонтального переполнения всей страницы, таблицы читаемы,
нет ошибок JavaScript и внешних загрузок, а хеши включённых Markdown и исходников
совпадают с текущими файлами. Нужен и визуальный просмотр мобильного отображения.

Пользовательские `example/` и старый `example.pdf` явно игнорируются Git.
Не добавляйте их принудительно. Результаты конвертаций, переводов, журналы
прогресса и отчёты храните в игнорируемом `output/`, временные проверки — в `tmp/`.
Для пользовательского пути вне этих каталогов отдельно проверьте исключение
перед коммитом; не игнорируйте все MD/TXT, поскольку среди них есть документация.

`output/` остаётся игнорируемым каталогом: обновить локальный HTML не означает
принудительно добавить его в Git. Обновление документации также не разрешает
независимый аудит, перегенерацию `output/example.*`, коммит или push без
соответствующей прямой команды.

Перед сдачей полезны `git diff --check`, просмотр diff документации и полный
набор тестов. Коммит и push выполняются только при прямом поручении пользователя.

При изменении границ модулей поддерживайте архитектурные тесты и [SOLID-контракты](solid.md).
Имена production-модулей не должны возвращаться в независимые fixtures через
наследование конкретного SDK-адаптера. Низкоуровневый SDK тестируется отдельно.
